### SEC-GRANT-PUBLIC-01 — `revoke ... from anon` во всём репо оставляет PUBLIC execute
**Context:** канонический паттерн `grant execute to authenticated; revoke execute from anon` НЕ снимает дефолтный `GRANT EXECUTE ... TO PUBLIC`, который Postgres/Supabase вешает на каждую функцию при создании. Подтверждено на проде: у `rpc_get_grade_formula`, `rpc_get_demand_board` и др. ACL содержит `=X/postgres` (PUBLIC) → `has_function_privilege('anon', …)` = true, несмотря на `revoke from anon`. Не эксплойт там, где у SECURITY DEFINER функции есть внутренний org-guard (`fn_my_org_ids()`/`fn_is_admin()`) — guard отклоняет анонима. Эксплойт — только у SECURITY DEFINER без guard (были C1/C2/S1 в биллинге, уже закрыты).
**Retire-when:** аудит всех SECURITY DEFINER RPC без внутреннего guard → добавить `revoke execute ... from public` (не только anon) там, где функция раскрывает per-tenant данные или пишет. Опционально: `ALTER DEFAULT PRIVILEGES ... REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` + явные гранты. Проверять новые RPC на этот паттерн в ревью (cross_check-правило не добавлял — зафлагает сотни существующих функций шумом).
**Severity:** medium (системно; фактический риск локализован незащищёнными функциями — их надо найти). **Owner surface:** все d-файлы (grant/revoke-блоки).

### PWA-STALE-VERSION-01 — после выкладки пользователи продолжают видеть СТАРУЮ версию, пока не закроют все вкладки
**Context:** найдено эмпирически 03.09.2026 сразу после мержа #176: владелец открыл `turanstandard.kz/mpk/profile/overview` и увидел **мобильную оболочку закупок** вместо новой консоли. Диагностика показала, что выкладка была ни при чём — на сервере лежал свежий бандл (`/mpk/profile` и чанк `MpkProfileApp-*.js` присутствовали, проверено прямым `fetch` мимо кэша). Дело в service worker.

Механика, три части, каждая по отдельности безобидна:
1. `vite.config.ts` → `VitePWA({ workbox: { navigateFallback: '/index.html' } })` — SW **сам отвечает на любую навигацию**, отдавая `index.html` из precache. То есть даже прямой ввод URL не доходит до сети.
2. **Нет `skipWaiting` и `clientsClaim`** — новый SW после выкладки устанавливается, но переходит в состояние `waiting` и не активируется, пока открыта хотя бы одна вкладка сайта. Старый продолжает обслуживать.
3. `HostContext.tsx:44-51` — регистрация сведена к `navigator.serviceWorker.register('/sw.js')`: **нет подписки на `updatefound`/`waiting`, нет предложения обновиться, нет перезагрузки по активации**. Пользователю не сообщают, что версия устарела.

Следствие: **после КАЖДОЙ выкладки** любой пользователь, у которого сайт уже открывался, продолжает работать на старой версии неопределённо долго. Новый маршрут в старом бандле не существует, поэтому `/mpk/profile/*` перехватывает общий `/mpk/*` и показывает не тот экран — то есть симптом выглядит как «выкладка не доехала» или «сломался роутинг», и диагностируется не в ту сторону (что и произошло 03.09). Лечится у пользователя только `Ctrl+Shift+R`, закрытием ВСЕХ вкладок домена или ручным `Unregister` в DevTools.

**Retire-when:** выбрать и реализовать стратегию обновления — это **продуктовое решение, не техническое**: (а) тихое авто-обновление (`skipWaiting` + `clientsClaim` + перезагрузка по `controllerchange`) — просто, но перезагружает страницу под пользователем и может прервать заполнение формы (для кабинета с длинными формами MP-3.3 это реальный риск потери ввода); (б) предложение «доступна новая версия — обновить» (подписка на `registration.waiting`, кнопка → `postMessage({type:'SKIP_WAITING'})` → перезагрузка) — безопаснее, но требует UI и места под него в обеих зонах. Рекомендация: (б). До реализации — при каждой выкладке предупреждать пользователей, что нужна жёсткая перезагрузка.
**Severity:** high (затрагивает **каждый** релиз и **каждого** пользователя; выкладка де-факто не доходит до людей, а симптом маскируется под другие дефекты). **Owner surface:** `vite.config.ts` (`VitePWA.workbox`), `src/platform/host/HostContext.tsx:44-51` (регистрация SW). **Tracking:** найдено 03.09.2026 при выкладке ARS-623; сам SW введён ARS-147 (`DECISIONS_LOG` 2026-07-03), где обновление не рассматривалось.
