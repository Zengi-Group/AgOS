## Ключевая причина массового SKIP

Backend реальный (не demo) → ui+rpc-кейсы бьют по настоящему Mobizon (SMS) и создают
настоящего auth-пользователя на подключённом проекте — оба действия запрещены правилами
прогона без staging-контура (`qa/README.md` §4a п.4: мок Mobizon/тестовый номер отсутствует;
`SKILL.md` п.1: мутации вне rollback-tx — только staging, SMS — не триггерить, бюджет).
Весь флоу после экрана «Контакт» (OTP-верификация → PIN → роль → детали роли → согласия →
сабмит) физически недостижим в UI без прохождения через живую отправку/проверку OTP —
поэтому все кейсы, которые предполагают нахождение на этих шагах, ушли в SKIP(sms), а не
были подтверждены даже статическим чтением кода (правило: evidence = снапшот/лог, не код-ревью).
Storybook в репо не сконфигурирован как отдельный dev-сервер в `.claude/launch.json`, поднимать
собственную инфраструктуру вне скоупа задания не стал.

Прогнаны напрямую (реальные DOM-взаимодействия, evidence = snapshot/network) только кейсы
экрана «Контакт» (`Contact.tsx`), которые проверяются ДО вызова `bird-otp` (клиентская валидация)
или не требуют его вовсе.

## Находки (кандидаты в дефекты / IMPL_DEBT)

- **REG-OTP-04 (FAIL, подтверждено):** `PhoneInput.tsx` не нормализует номер, введённый начиная с
  «8» (частая привычка при вводе казахстанских номеров) — ведущая цифра «8» сохраняется как есть,
  что при сабмите даёт `+78XXXXXXXXX` вместо корректного `+7 7XXXXXXXXX`. Затрагивает: `handleSendOtp`,
  `handleResend` (Contact.tsx:51,96 — `+7${formData.phone}`) и `handleRegister`
  (Registration.tsx:191). Кейс написан по `canon:code`, т.е. ожидание = поведение прода, а не канон
  документа — значит расхождение НЕ покрыто существующим IMPL_DEBT (проверено grep, 0 совпадений) и
  должно быть заведено как новая строка долга. Не чинил (правило «прогон не чинит»).
- **Инфраструктурное наблюдение (не FAIL кейса, вне scope REG-*):** публичный лендинг `/` показывает
  нерезолвленные i18n-ключи (`constants.regions.Актюбинская область`, `constants.regions.Алматинская
  область`) в блоке "FOR FARMERS"/"FOR PROCESSORS" — увидено случайно при навигации к `/register`.
  Не относится к файлу 01-registration.md, флагаю отдельно, не завожу как находку этого прогона.

## Предложения по кейсам (устаревшие ожидания, смена status)

- Ни один активный кейс не выглядит устаревшим по канону — расхождение REG-OTP-04 это дефект
  реализации, не смена ожидания.
- **Процессное предложение:** цепочка REG-OTP-06..REG-SUB-07 архитектурно не прогоняема как «чистый
  UI» без мок-провайдера OTP (тестовый номер/фиксированный код) — рекомендую завести dev-only bypass
  в `bird-otp` (например, спец. номер `+7700...` возвращающий детерминированный код) под флагом
  окружения, аналогично дисциплине staging seed-аккаунтов из `qa/README.md` §3. Без этого весь layer
  `ui+rpc`/`ui` после экрана «Контакт» остаётся SKIP при каждом будущем прогоне, если нет staging
  с мок-SMS.
