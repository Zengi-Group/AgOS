## Находки (кандидаты в дефекты / IMPL_DEBT)
- Нет находок в проверенном коде. Логика AUTH-LOG-02/03/04 и AUTH-ADM-02 соответствует
  `canon:code` (ожидание кейса = поведение кода, реальным прогоном подтверждено 1:1).
- **Инфраструктурный гэп, не код-дефект**: нет seed-скрипта/seed-данных для
  farmer/mpk тестовых аккаунтов (`scripts/` содержит только `seed_admin.mjs`). Это
  блокирует happy-path UI-прогон AUTH-LOG-01 при любом будущем запуске без ручной
  подготовки данных. Не заводил как IMPL_DEBT — это тест-инфраструктура, не
  расхождение канон↔код; если считаете нужным зафиксировать — отдельная задача
  «seed-скрипт для QA farmer/mpk аккаунтов», не в рамках этого прогона.

## Предложения по кейсам (устаревшие ожидания, смена status)
- AUTH-LOG-01, AUTH-ADM-01, AUTH-RST-01, AUTH-RST-03 технически `status:active`, но при
  отсутствии staging-окружения с seed-аккаунтами/кредами и без разрешения на живые
  SMS они систематически не прогоняемы через UI end-to-end. Не предлагаю менять
  `status` (канон и код не расходятся — это вопрос доступности тестовых данных, не
  дефект), но фиксирую как повторяющийся блокер: следующему прогону нужны заранее
  (1) seed farmer/mpk аккаунт с известным телефоном+PIN, (2) `ADMIN_PASSWORD` в
  окружении агента, (3) явное разрешение/мок для одной живой отправки OTP на тестовый
  номер, либо тестовый режим bird-otp, возвращающий код без отправки SMS.
- AUTH-RST-01/03 логику UI (`ForgotPin.tsx`) можно было проверить более глубоко юнит-тестом
  компонента (mock `supabase.functions.invoke`) — вне мандата ручного UI-прогона
  (`auto:none` в кейсе), но это кандидат для `auto:candidate:browser`, если появится
  тестовый режим OTP.
