# AgOS QA — тест-сценарии (канон + реальность)

> Единый дом тест-кейсов флоу: **регистрация → онбординг → членство → продажа скота (TSP)**.
> Кейсы пишутся по каноническим документам (Microstep 1/2/4/6, Dok 6-слайсы) и сверяются
> с реальностью кода. Пригодны для ручного прогона И для автоматизации.

## 2. Формат кейса

Каждый кейс — секция `####` с машинно-парсимой строкой метаданных:

```markdown
#### MEM-T2-01 · HAPPY · Одобрение заявки создаёт членство
`layer:rpc+ui` `canon:MS2-T2;Dok6S2-A02` `impl:d01_kernel.sql` `auto:none` `status:active`

- **Предусловие:** заявка организации в статусе submitted.
- **Шаги:** 1) Админ открывает /admin/membership/:id  2) «Одобрить» → подтвердить.
- **Ожидание:** создан AssociationMembership (grace_period, grace_until=+30д); ...
```

### Поля метаданных

| Поле | Значения | Смысл |
|---|---|---|
| ID | `<ДОМЕН>-<ГРУППА>-<NN>` | стабильный, никогда не переиспользуется после удаления |
| ТИП | `HAPPY` / `UNHAPPY` / `EDGE` | как в исходном концепте |
| `layer:` | `ui`, `rpc`, `ui+rpc`, `e2e`, `sql` | где проверяем (UI-поведение / контракт RPC / сквозной) |
| `canon:` | `MS2-T5`, `Dok6S2-A01`, `D-M6-5`, `code` | раздел канона; `code` = поведение задано только кодом |
| `impl:` | файл(ы) реальности | где это живёт в коде |
| `auto:` | `none`, `tests/<file>`, `candidate:<вид>` | статус автоматизации |
| `status:` | `active`, `mock`, `blocked:<DEBT-ID>`, `future` | см. ниже |

### Статусы кейса — ключ к «канон ≠ код»

- **active** — можно прогонять прямо сейчас, ожидание = поведение прода.
- **mock** — проверяет намеренное MVP-поведение (мок оплаты, локальный классификатор
  категории, demo-фолбэк публикации). При появлении реального бэкенда ожидание меняется —
  кейс помечен, чтобы его нашли.
- **blocked:\<DEBT-ID\>** — кейс написан по канону, но код расходится (см. `IMPL_DEBT.md`).
  НЕ прогонять как баг: это known gap. При закрытии долга кейс переводится в active.
- **future** — канон/дизайн есть, слайс не начат.

Правило: **кейс всегда описывает канон**; если реальность отличается — статус blocked
и ссылка на IMPL_DEBT, а не «подгонка» ожидания под код. Если расхождение не
зарегистрировано в IMPL_DEBT — это находка: завести строку долга (процесс из CLAUDE.md:
конфликт флагуется, не решается молча).

## 3. Ручной прогон

Прогоняются кейсы `status:active` и `status:mock` своего слоя:
- `layer:ui` / `ui+rpc` — руками в preview/проде по шагам кейса;
- `layer:rpc` / `sql` — через SQL-консоль / psql (шаги = вызовы RPC);
- чек-лист прогона: копия файла или пометки ✅/❌ по ID в отчёте прогона.

Тайминги и лимиты (OTP TTL 5 мин, offer_window 24 ч, шаг цены 100 ₸/кг, лимит 5 партий…)
— **standards-as-data (P8)**: в кейсах указаны текущие значения, но прогон обязан сверять
актуальный конфиг (`tsp_config` и т.п.), а не хардкод кейса.

## 4. Автоматизация

Инфраструктура уже в репо:

| Слой | Инструмент | Команда |
|---|---|---|
| unit | Vitest (project `unit`) | `npm run test:unit` |
| browser/UI | Vitest + Playwright (project `routers`) | `npm run test:routers` |
| backend E2E | SQL rollback-tx | `psql "$DATABASE_URL" -f tests/tsp_happy_path_test.sql` |

Связь автотеста с кейсом — тег в коде теста:

```sql
-- @case E2E-TSP-01 E2E-TSP-02
```
```ts
// @case AUTH-LOG-01
```

`qa/check_coverage.sh` собирает все ID из `qa/scenarios/` и все `@case`-теги из
`tests/`, `src/**/*.test.*`, `supabase/functions/**` — и печатает: покрыто / не покрыто /
теги-сироты (тег есть, кейс удалён).

Приоритет автоматизации (рекомендация): 1) SQL rollback-tx на FSM-переходы (членство,
партия) — дёшево и бьёт по самому ценному; 2) browser-тесты визарда партии и регистрации;
3) негативные RPC-кейсы (SEC-*) — прямые вызовы под чужой ролью.

## 4a. Прогон агентами

Два входа:
- **Один домен:** `/qa-run <файл|домен>` — агент по процедуре `.claude/skills/qa-run/SKILL.md`
  парсит файл, исполняет active/mock-кейсы по слоям (sql/rpc — rollback-tx через psql;
  ui — preview-сервер), пишет отчёт в `qa/runs/<дата>-<файл>.md`.
- **Всё сразу:** workflow `qa-run-all` (`.claude/workflows/qa-run-all.js`) — backend-слой
  всех файлов параллельно, UI волнами по трём портам, в конце сводка
  `qa/runs/<дата>-SUMMARY.md` + check_coverage.sh.

Предпосылки полного прогона (без них соответствующие кейсы честно уходят в SKIP):
1. `DATABASE_URL` **staging**-базы в окружении (sql/rpc-слой; мутации вне rollback-tx —
   только staging, прод — никогда);
2. `.env` с `VITE_SUPABASE_*` staging (UI против реального бэкенда; иначе demo-режим →
   PARTIAL);
3. seed-аккаунты: фермер-не-член, фермер-член(active), МПК, админ;
4. мок Mobizon / тестовый номер для OTP-кейсов.

Правила исполнителя: прогон ничего не чинит (FAIL + evidence, починка отдельно);
расхождение сверяется с IMPL_DEBT (зарегистрировано → KNOWN-GAP, нет → находка).

## 5. Поддержка актуальности (правила)

1. **Кейсы живут в том же репо и меняются тем же PR**, что меняет поведение флоу.
   Definition of Done фичи = обновлён соответствующий файл в `qa/scenarios/`
   (аналогично правилу «после SQL — cross_check.sh»).
2. **Один факт — один дом (P4):** ожидания не дублируют канон дословно, а ссылаются на
   раздел (`canon:MS2-T5`). Меняется канон → кейс находит устаревание по ссылке.
3. **IMPL_DEBT ↔ status:blocked** синхронны: закрыл долг — переведи кейсы в active
   (grep по `blocked:<DEBT-ID>` находит все).
4. **ID стабильны.** Удалённый кейс не переиспользуется; новый кейс = новый номер.
5. Раз в слайс — прогон `qa/check_coverage.sh` и беглый lint: нет ли кейсов без
   canon-ссылки и blocked-кейсов с закрытым долгом.
