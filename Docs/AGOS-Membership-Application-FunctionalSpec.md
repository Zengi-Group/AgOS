## 0. Модель членства (контекст для дизайнера)

Членство **бинарное**: организация либо член, либо нет (канон D-MEM-1). Уровней нет.
Доступ к Рынку (TSP), справочным ценам и защите сделок открывается **только**
членством — не личной подпиской.

**Статусы, которые видит пользователь** (`MembershipStatus`, shell):

| Статус | Смысл | Доступ к TSP |
|---|---|---|
| `none` | не член (не подавал / отклонён / откатился) | ❌ |
| `pending` | заявка подана, на рассмотрении у ТУРАН | ❌ |
| `approved` | заявка одобрена, взнос ещё не оплачен | ⚠️ см. Флаг F-2 |
| `active` | взнос оплачен, членство действует | ✅ |
| `expiring` | активно, но срок скоро истекает (UI-подсостояние active) | ✅ |
| `grace` | срок истёк, окно продления (доступ ещё есть) | ✅ |
| `expired` | окно продления прошло, доступ закрыт | ❌ (текущие сделки доводятся) |
| `rejected` | заявка отклонена | ❌ |
| `terminated` | членство прекращено админом | ❌ |

Переходы, сроки и авторитеты — канон Microstep 2, §2–§5. Дизайнер их не меняет,
но должен покрыть экранами все статусы из таблицы.

## ⚠️ Флаги (расхождения канон ↔ код — решает CEO/архитектор, не дизайнер)

**F-1 — Документы идут мимо RPC.** Канон Microstep 2 T1 описывает
`rpc_submit_membership_application(org_id, documents[])`. В реальности RPC —
`(p_organization_id, p_membership_type, p_notes)`, а документы грузятся отдельно в
Storage `membership-documents/{orgId}/docs/`. Функционально флоу работает, но канон
T1 неточен. Требует правки канона. **На дизайн не влияет.**

**F-2 — Доступ в статусе `approved` (до первой оплаты).** Канон D-MEM-3: после
одобрения даётся 30-дневный доступ к capabilities ДО оплаты (grace_period,
capabilities ON). Код же трактует `approved` как «продажа закрыта, оплатите, чтобы
открыть» (copy: «оплатите взнос, чтобы открыть продажу»). Это прямое противоречие.
**Влияет на копи и на то, что доступно на экране одобрения.** Нужно решение CEO:
доступ в `approved` — открыт (канон) или закрыт до оплаты (код)?

**F-3 — Шаг «подписание» (signing).** `application-flow.ts` объявляет 4 шага:
`documents → signing → payment → review`, но `signing` (э-подпись/договор) не
построен. Открытый вопрос: входит ли подписание оферты/договора в флоу? Сейчас
спроектировано БЕЗ него.

## Экраны

### S1. Гейт членства (точка входа)

**Назначение.** Перехватить попытку не-члена воспользоваться функцией «для членов»
и объяснить, как получить доступ.

**Точка входа.** Пользователь (`none` / `pending` / `expired` и т.п.) пытается
выполнить действие, закрытое членством: создать/опубликовать партию, увидеть
справочные цены, войти в Рынок (TSP). Показывается поверх (шторка).

**Что на экране (функционально).** Зависит от статуса:
- `none` → заголовок «Доступно членам TURAN»; пояснение, что продажа партий,
  справочные цены и защита сделок — для членов; действие **«Подать заявку»** → S2.
- `pending` → «Заявка на рассмотрении»; пояснение «продажа откроется после
  одобрения и оплаты; ответим в течение 3 рабочих дней»; **действия-CTA нет**,
  только закрыть.
- `expired` → «Членство истекло»; пояснение «текущие сделки можно довести до конца,
  для новых партий — оплатите»; действие **«Оплатить»** → S6.
- Закрытие: вторичное «Понятно».

**Данные.** Только `membership` (статус). Ничего не сохраняет.

**Состояния/края.** Каждый статус = свой набор «заголовок + текст + CTA/без CTA».
CTA присутствует не всегда (у `pending` его нет).

**Критерии приёмки.** Для каждого статуса из §0 определено: заголовок, поясняющий
текст, есть ли CTA и куда он ведёт. Ни один статус не оставляет пользователя без
понимания следующего шага.

### S2. Сбор документов и подача заявки

**Назначение.** Собрать обязательные документы организации и отправить заявку на
рассмотрение в ТУРАН. Это и есть «подача заявки».

**Точка входа.** «Подать заявку» из S1 (`none`), либо «Подать заново» из состояния
`rejected` (S4), либо «Подать заявку» из `terminated`.

**Что на экране (функционально).**
- Пояснение: заявка в ассоциацию; после одобрения откроется оплата взноса и Рынок.
- Список **обязательных документов** (все 3 required), по каждому — название,
  подсказка, статус (загружен / нет), действие «Загрузить» / «Заменить»:
  1. **Документ о гос. регистрации (с БИН)** — свидетельство/справка с БИН.
  2. **Удостоверение личности руководителя** — лицевая и обратная сторона.
  3. **Банковские реквизиты** — реквизиты счёта для расчётов.
- Индикатор прогресса «N / 3 готово».
- Ограничения формата видимы: **PDF, JPG, PNG · до 10 МБ**.
- Главное действие: **«Отправить на проверку»** — активно только когда загружены
  все 3 документа.
- Вторичное: «Отмена».

**Данные.**
- Файлы → Storage bucket `membership-documents`, путь `{orgId}/docs/{slotKey}_{ts}.{ext}`.
  Повторная загрузка слота заменяет прежний файл.
- При открытии — подтягиваются уже загруженные файлы (возврат к незавершённой заявке).
- Отправка → `rpc_submit_membership_application(orgId, 'associate', notes=null)`.
- Захват файла: на мобильном/нативном — камера или галерея; на web — выбор файла.

**Логика/правила.**
- Кнопка отправки заблокирована, пока `doneCount < 3`.
- Ошибка `PENDING_EXISTS` (заявка уже на проверке) → трактуется как успех: документы
  обновлены, статус остаётся `pending`.
- Ошибка `ALREADY_ACTIVE` (членство уже активно) → сообщение «Членство уже активно»,
  заявка не создаётся.
- Одна активная заявка на организацию одновременно (канон §6): пока текущая не
  закрыта (approved/rejected) — новую подать нельзя.

**Состояния/края.** Пусто (0/3) · частично (1–2/3) · загрузка слота (спиннер на
слоте) · ошибка загрузки файла (сообщение, слот остаётся пустым) · файл > 10 МБ
(отклонить с сообщением) · отправка (индикатор на кнопке) · офлайн (загрузка/отправка
недоступны — сообщение о соединении) · возврат к заявке (ранее загруженные видны как
«Загружено — нажмите, чтобы заменить»).

**Критерии приёмки.** Нельзя отправить без всех 3 документов. После успешной отправки
статус организации → `pending`, пользователь уходит из формы в состояние «на
рассмотрении» (S3). Файлы переживают закрытие и повторное открытие формы.

### S3. Состояние «Заявка на рассмотрении» (`pending`)

**Назначение.** Показать, что заявка ушла и что делать (ничего — ждать).

**Точка входа.** Сразу после S2; и при любом входе, пока статус `pending`.

**Что на экране (функционально).**
- На Главной (лента «идёт само»): пункт «Заявка на рассмотрении · ответ в течение
  3 рабочих дней».
- При попытке действий «для членов» — гейт S1 в варианте `pending` (без CTA).

**Данные.** Статус `pending`; (опц.) дата подачи для отсчёта срока.

**Состояния/края.** Долгое ожидание (> заявленных 3 дней) — копи не обещает точную
дату, формулировка «в течение N рабочих дней». Никаких действий пользователя не
требуется и не предлагается.

**Критерии приёмки.** Пользователь в `pending` нигде не видит тупика: он понимает,
что заявка на рассмотрении и когда ждать ответа. Действия «для членов» вежливо
заблокированы.

---

### S4. Состояние «Заявка отклонена» (`rejected`)

**Назначение.** Сообщить об отказе, назвать причину и дать подать заново.

**Что на экране (функционально).**
- Карточка на Главной (ярус «требует решения»): «Заявка отклонена», строка причины
  (пример из кода: «нужна выписка о регистрации хозяйства»), действие **«Подать
  заново»** → S2.

**Данные.** Статус `rejected`; **причина отказа** (текст от админа ТУРАН).

**Логика/правила.** Отказ откатывает организацию в `none` (канон D-MEM-4), история
отказа хранится в `MembershipApplication`. Повторная подача разрешена без ограничений.

**Состояния/края.** Причина отказа задана всегда (админ обязан её указать) —
дизайнер закладывает наличие текста причины; пустая причина = деградированный, но
допустимый случай (показать общий текст).

**Критерии приёмки.** Пользователь видит, ПОЧЕМУ отказано, и может начать новую
заявку одним действием. Причина отображается.

---

### S5. Состояние «Заявка одобрена — оплатите взнос» (`approved`)

**Назначение.** Сообщить об одобрении и провести к оплате взноса.

**Что на экране (функционально).**
- Карточка на Главной (высший приоритет): «Заявка одобрена — оплатите взнос, чтобы
  открыть продажу», срок «до <дата>», действие **«Оплатить взнос»** → S6.
- ⚠️ Формулировка про доступ зависит от решения по **Флагу F-2** (доступ открыт до
  оплаты или нет).

**Данные.** Статус `approved`; **срок оплаты** (`grace_until` = дата одобрения + 30
дней, канон T2).

**Логика/правила.** Если до `grace_until` оплаты нет — членство уходит в `revoked`
(канон T5, `first_payment_timeout`) и требуется новая заявка.

**Состояния/края.** Приближение дедлайна (счётчик «осталось N дней»); истечение без
оплаты → переход в `terminated`-подобный сценарий (новая заявка).

**Критерии приёмки.** Пользователь понимает, что одобрен, до какого числа платить и
что будет, если не заплатить. Одно действие ведёт к оплате.

---

### S6. Оплата членского взноса

**Назначение.** Принять оплату годового членского взноса и активировать членство.

**Точка входа.** «Оплатить взнос» из S5 (`approved`); «Оплатить/Продлить» из
`expiring`/`grace`/`expired` (продление).

**Что на экране (функционально).**
- Заголовок: «Членский взнос» (первичная) / «Продление членства» (продление).
- Что даёт: «Доступ к Рынку (TSP), справочным ценам и сообществу ассоциации на 12
  месяцев».
- Сумма к оплате: **120 000 ₸** · членство на год. (⚠️ сумма/срок — параметр,
  см. Q-MEM-FEE / Q-MEM-DURATION; заложить как данные, не как константу.)
- Выбор способа оплаты: **Kaspi Pay** · **Банковская карта** (Visa/Mastercard) ·
  **Счёт на оплату** (для юр. лиц). По умолчанию выбран первый.
- Действие: **«Оплатить 120 000 ₸»** → активация → S7.
- Вторичное: «Отмена».

**Данные.** Сумма, срок (12 мес), выбранный способ; статус `membership` (определяет
заголовок первичная/продление). Подтверждение оплаты → членство `active`,
`paid_until = дата оплаты + срок` (канон T4/T7/T9).

**Логика/правила.** На пилоте оплата — **мок** (реальной платёжной системы нет):
выбор способа → «Оплатить» → успех. Реальная интеграция (Kaspi webhook) —
последующий этап. Дизайн закладывает реальный флоу оплаты (успех/ошибка/ожидание
подтверждения), даже если бэкенд пока мок.

**Состояния/края.** Выбор способа · обработка оплаты · успех · ошибка/отклонение
оплаты · оплата вне приложения (счёт на оплату — оплата приходит позже, статус пока
не `active`). Продление из `expired` — доступ откроется после подтверждения.

**Критерии приёмки.** Видна сумма, срок и что даёт членство. Выбран способ оплаты.
Успешная оплата ведёт к активному членству (S7) и открытию Рынка.

---

### S7. Членство активно (успех) + сопутствующие статусы

**Назначение.** Подтвердить активацию и показать состояние действующего членства.

**Что на экране (функционально).**
- Подтверждение активации; Рынок (TSP) и функции «для членов» открыты.
- Действующее членство: срок действия «до <дата>» (`paid_until`).
- `expiring` (срок скоро истекает): карточка «Продлите членство» → S6.
- `grace` (срок истёк, окно продления): «Продлите членство — иначе доступ закроется»,
  срок «до <дата>» → S6.
- `expired` (доступ закрыт): «Членство истекло — оплатите, чтобы вернуть продажу;
  текущие сделки можно довести до конца» → S6.
- `terminated` (прекращено админом): «Членство прекращено; чтобы вернуться — подайте
  заявку заново» → S2.

**Данные.** Статус `membership`, `paid_until` / `grace_until`.

**Критерии приёмки.** Активный член видит срок действия. Каждый пограничный статус
(`expiring`/`grace`/`expired`/`terminated`) имеет понятный призыв: продлить или подать
заново.

## Карта переходов (для дизайнера, упрощённая)

```
[не член none] --Подать заявку--> S2 документы --Отправить--> [pending]
[pending] --админ одобрил--> [approved] --Оплатить--> [active]
[pending] --админ отклонил--> [rejected] --Подать заново--> S2
[active] --срок скоро--> [expiring] --Продлить--> [active]
[active] --срок истёк--> [grace] --Оплатить--> [active]
[grace] --окно прошло--> [expired] --Оплатить--> [active]
[approved] --не оплатил 30д--> [terminated/новая заявка]
[любой активный] --админ прекратил--> [terminated] --Подать заявку--> S2
```
