# ТСП · Отказы базы — словами оператора МПК (ARS-691)

<frozen-after-approval>

## Intent
Когда база отказывает оператору мясокомбината (отправить предложение, принять, закрыть заявку,
подтвердить приёмку), он сегодня видит машинную строку: «Не удалось отправить оффер:
BATCH_FULLY_MATCHED», «ALLOC_FAILED: строка не смогла принять кусок…», латинский сорт `vysshaya`.
Слайс заменяет её фразой, по которой оператор понимает, **что случилось и что делать дальше**. Если
код системе не знаком, оператор всё равно видит осмысленную фразу, а разработчик видит код (по
скриншоту и в консоли). Решения владельца 2026-09-24: словарь живёт в коде фронта; незнакомый
код показывается мелко под фразой; фермерская зона не входит.

## Boundaries & Constraints
**Always**
- FR-001 Каждый отказ RPC, который показывается оператору в точках вывода из таблицы P, проходит
  через **один** общий словарь зоны МПК. Текст на экране = существующий префикс действия (как
  сегодня, например «Не удалось отправить оффер: ») + фраза из таблицы D.
- FR-002 Код = текст до первого двоеточия, без пробелов по краям, и только если он имеет вид
  `^[A-Z][A-Z0-9_]*$`. Словарь выбирает фразу по тексту кода, **не** по `errcode`.
- FR-003 Текст после двоеточия (технический хвост: английский, «кусок», латинский сорт) оператору
  не показывается никогда.
- FR-004 Код, которого нет в таблице D → фраза `FALLBACK` и под ней отдельная строка
  «Код: <КОД>» (только код, без хвоста): 12px, цвет контейнера без приглушения (канон
  `DesignRules-FarmerCabinet` R-21: мелкий серый текст — дефект), в тосте, плашке десктопа и
  подсказке формы. Сообщение без кода (например, нарушение CHECK) →
  фраза `FALLBACK` без строки кода.
- FR-005 Сетевой сбой (запрос не дошёл до базы) → фраза `NETWORK` без строки кода.
- FR-006 При каждом показанном отказе полный исходный текст ошибки пишется в `console.error`.
- FR-007 Поведение экранов при отказе не меняется: окно остаётся открытым, кнопка снова
  доступна, сделка не объявляется. В мобильном мониторе пула сохраняется существующее подавление
  `INVALID_STATUS` для уже принятой строки. На десктопе (`RequestMonitor`) подавления нет и не
  появляется: там показывается фраза `INVALID_STATUS`.
- FR-008 Слайс заменяет `ARS-687 M-010` только в части «строка отказа из базы дословно»
  (решение G1, 2026-09-24). Остальное в `M-010` («экран не объявляет сделку») остаётся в силе.
- FR-013 Собственные тексты фронта (брошенные нашим кодом, а не базой, например «Заявка создана,
  но не опубликована (нет pool_id)» или запасная фраза `fail()` в `pool-actions.ts`) показываются
  как есть, мимо словаря.
- FR-014 Тост, его тип и стиль общие с фермерской зоной (`Toast.tsx`, `ToastState`, `cabinet.css`;
  канон `AGOS-DesignRules-FarmerCabinet.md` покрывает и шелл МПК). Фермерские тосты выглядят как
  сегодня: строка кода появляется, только если её передали.

**Never**
- FR-009 Не меняет ни одного RPC, текста исключения, `errcode` или таблицы. Только фронт.
- FR-010 Не меняет причины недоступности кнопки (`ARS-687 FR-002`), тосты успеха и префиксы
  действий.
- FR-011 Не трогает фермерскую зону и профиль МПК: у `OrgSection` остаётся свой словарь
  (правило ARS-362 «тексты ошибок на клиенте, база шлёт код»).
- FR-012 Не чинит префикс «Заявка не заведена:» у десктопной формы, когда отказывает запуск уже
  созданной заявки. Это существующая неточность, у неё отдельная задача (ledger).

**Таблица P · точки вывода** (мобильный шелл МПК и десктоп-консоль «Мои заявки»):
отправить предложение (`BatchDetailModal`) · принять и отклонить предложение (`MpkApp`) ·
обновить статус, закрыть сейчас, принять набранное или вернуть партии, подтвердить приёмку,
отправить отзыв (`PoolMonitorModal`) · создать и запустить заявку (`CreatePoolModal`) · десктоп:
принять набранное или вернуть, подтвердить приёмку (`RequestMonitor`), завести заявку
(`CreateRequestModal`).

## Design contract (сигнатуры, НЕ тела)
- **Data model:** нет. Ни таблиц, ни колонок (FR-009).
- **API / RPC:** не меняются. Новый модуль фронта `src/pages/cabinet/shell/mpk/data/rpc-error-text.ts`:
  `rpcErrorText(raw: unknown): { text: string; code: string | null }`. `text` — фраза по таблице D,
  `code` — строка для мелкой строки (только по FR-004), иначе `null`. Разбор кода — свой, внутри
  модуля: до двоеточия плюс проверка вида из FR-002 (у `parseRpcCode` профиля проверки вида нет,
  это другая функция; профиль не трогаем, FR-011). Запись в консоль по FR-006.
  Там же `class LocalError extends Error` — пометка собственного текста фронта (FR-013):
  `rpcErrorText` отдаёт `message` такого объекта как есть, без строки кода. `LocalError` бросают
  ровно пять мест: запасная ветка `fail()` (`pool-actions.ts`, только когда текста базы нет),
  `pool-actions.ts` «пустой ответ сервера» и «нет pool_id», `CreatePoolModal` «пустой ответ
  сервера» и «нет pool_id» (SC-001).
- **Events:** нет.
- **UI contract:** в `MpkApp` локальный тип тоста `{ id; text }` получает `code?: string`, а
  `showToast(text, code?)` — необязательный второй аргумент. Проп модалок
  `toast: (text: string, code?: string) => void` расширяется так же, старые вызовы не ломаются.
  Общий `ToastState` / `Toast` получают необязательное `code` и рисуют его второй строкой по
  FR-004. Та же вторая строка появляется в плашке десктопа `mpkr-flash bad` и в подсказке формы
  `mpk-error-hint` (`CreatePoolModal`). Все точки из таблицы P вместо `e.message` берут
  `rpcErrorText(e)`.
