# Монитор пула — двухмаршрутная read-model — комбинат снова видит своих поставщиков

<frozen-after-approval>

## Intent

С 26 июля оператор мясокомбината открывает набранный пул и видит «заполнен, контакты
раскрыты» — над **пустым списком поставщиков**: запись вернулась в модель «партия целиком
привязана к строке пула», а читающая функция монитора осталась в модели кусков. Данные о
сделке в базе есть — их некому показать. Отсюда всё остальное: комбинат не узнаёт, у кого
купил (хотя фермер своего покупателя видит), не может подтвердить приёмку и оставить отзыв,
а без приёмки недостижима и репутация обеих сторон.

Слайс возвращает монитору зрение — он читает **обе** формы связи — и делает приёмку и отзыв
достижимыми на обоих маршрутах. Дробление партий при этом **не включается**: решение CEO от
26.07 в силе, монитор лишь читает записанное. Разбор корня и доказательства — ARS-684.

## Boundaries & Constraints

**Always**
- **FR-001** Монитор показывает поставщиков для обоих маршрутов набора: есть распределения
  (`batch_allocations`) — по ним; нет — по привязке партии к строке пула
  (`batches.pool_line_id → pool_lines`). Образец приёма — `fn_ars_360_mpk_counterparty_ids`.
- **FR-002** Каждая строка несёт признак своего маршрута, чтобы приёмка адресовала кусок или
  партию, не угадывая.
- **FR-003** После раскрытия контактов пула комбинат видит название хозяйства и телефон в каждой
  строке — на обоих маршрутах (симметрия `D-M6-12`; сегодня фермер покупателя видит, комбинат
  фермера — нет).
- **FR-004** До раскрытия строки видны, хозяйство анонимно. Гейт `pools.mpk_contact_revealed_at`
  не ослабляется (`D-M6-5/12`, ст. 171).
- **FR-005** Приёмка достижима на обоих маршрутах; после неё строка показывает состояние из базы,
  а не локально угаданное.
- **FR-006** Отзыв комбината достижим после приёмки и подаётся канонически
  (`rpc_submit_deal_review`, уже двухмаршрутный). Тем самым достижима и взаимная репутация
  (`rpc_get_mpk_reputation`) — отдельной работы не требует.
- **FR-007** Управляющие элементы монитора у реального пула меняют только то, что реально
  меняется в базе. Дорисовывающие поставщиков, прогресс или сроки — доступны исключительно у
  демо-пула (seed, идентификатор не UUID), по образцу уже ограждённой кнопки «Демо: фермер
  отгрузил».
- **FR-008** Сигнатура `rpc_get_pool_matches(uuid)` не меняется; поля ответа только добавляются;
  существующая проекция `myRating` (ARS-360 / ADR-353, retire-дата 2026-10-31) сохраняется как есть
  (P7). *Снаружи не наблюдаемо — проверяется контракт-снапшотом в §Verification.*
- **FR-009** Комбинат видит строки только тех пулов, что принадлежат его организации; данные
  чужого пула не отдаются ни на одном маршруте.
- **FR-015** В строке поставщика показывается собственная прошлая оценка этого хозяйства
  (`myRating`, уже в ответе), а при её отсутствии — прочерк. Одинаковая константа рейтинга у всех
  хозяйств из монитора уходит.

**Never**
- **FR-010** Слайс **не включает дробление партий обратно** — решение CEO 26.07
  (`TSP-SLICE9-ROLLBACK-01`) в силе. Read-model только читает обе уже существующие формы записи.
- **FR-011** Слайс не трогает 6 канон-функций `d02_tsp.sql` (дом — ARS-314) и наследует его guard:
  `deploy.py --files d02_tsp.sql` и `--all` не запускаются. Деплой слайса — одна миграция поверх.
- **FR-012** Слайс не заводит новых таблиц, колонок и RPC (речь о схеме БД; поля *ответа*
  read-model добавляются — см. FR-008): обе функции приёмки
  (`rpc_self_confirm_delivery_alloc`, `rpc_self_confirm_delivery`) уже задеплоены.
- **FR-013** Слайс не чинит «фальшивую сделку» в `BatchDetailModal.tsx:61-73` (другой экран),
  не реализует выход из недобравшегося пула (`TSP-FLOW-10`), уведомления, планировщик и живые
  цены — каждое остаётся отдельной задачей.
- **FR-014** Слайс не регистрирует семейство `rpc_self_*` в `rpc_name_registry` и Dok 3 — это
  явный скоуп ARS-98 (Slice D).

## Design contract (сигнатуры, НЕ тела)

- **Data model.** Изменений нет: ни таблиц, ни колонок, ни FSM (P7, схема FINAL). Читаются
  `batch_allocations` и цепочка `batches.pool_line_id → pool_lines → pools`. Авторитет при
  конфликте (P2): есть распределения — источник они, `pool_line_id` = легаси-хвост (первый кусок);
  тот же порядок, что в `fn_ars_360_mpk_counterparty_ids`.
- **API / RPC.** `rpc_get_pool_matches(p_pool_id uuid) → jsonb` — сигнатура прежняя, строка ответа
  дополняется признаком маршрута (`source`: кусок либо партия), `matchId` остаётся уникальным
  ключом строки, существующие поля (вкл. `myRating`) сохраняются. Приёмка — задеплоенные
  `rpc_self_confirm_delivery_alloc(uuid)` (кусок) и `rpc_self_confirm_delivery(uuid)` (партия;
  гейт «пул моей организации» через `pool_line→pool`, `dispatched→delivered`, rollup пула в
  `completed`). Отзыв — `rpc_submit_deal_review` без правок. Новых RPC нет.
- **Events.** Слайс событий не добавляет. Известный разрыв (старше слайса, дом — ARS-98 / Dok 4):
  self-serve путь пишет только `batch_events`, `platform_events` не эмитит.
- **UI contract.** `PoolMonitorModal` (`mpk/modals/`), загрузка `mpk/data/pools-load.ts`, проводка
  `mpk/MpkApp.tsx`. Строка выбирает функцию приёмки по признаку маршрута. Состояния: пусто
  (`M-005`), ошибка/офлайн (`M-013`), загрузка (`M-016`), до раскрытия (`M-004`). Персона —
  оператор мясокомбината. Зона `/mpk` = Ionic-оболочка закупок: дизайн-система не меняется, новых
  экранов нет, топбар не затрагивается.

## Assumptions  (append-only, ВНЕ frozen)

- [2026-09-10] Статус строки маршрута «партия» выводится из `batches.status` (`confirmed`→ждёт
  отгрузки, `dispatched`→в пути, `delivered`→принята), по образцу маппинга статусов куска — чтобы
  UI не различал маршруты в отрисовке. Опровергнет: состояние партии, которому в этой шкале нет
  честного места.
- [2026-09-10] Партии в `matched` (пул не закрыт) показываются «активными», как сегодня активные
  куски. Опровергнет: решение скрывать строки до закрытия пула.
- [2026-09-10] Снятые партии исключаются, как исключаются куски `cancelled`. Опровергнет:
  требование показывать снятое историей.
- [2026-09-10] Дом контракта формы ответа `rpc_get_pool_matches` — этот спек: в Dok 3 функции нет
  вовсе, как и всего семейства `rpc_self_*` (регистрация — скоуп ARS-98, FR-014). Опровергнет:
  решение регистрировать read-функции в Dok 3 раньше Slice D.
