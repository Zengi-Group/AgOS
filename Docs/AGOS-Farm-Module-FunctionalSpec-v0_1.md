# AGOS — Модуль «Ферма». Функциональная спецификация (живой документ)

> Статус: **DRAFT v0.1** · Проектируется по методологии agos-ux (узел за узлом, реальность → функция).
> Это функциональная спека (ЧТО система делает и почему). Интерфейс — слой дизайнера, реализация — слой программиста; сюда не пишем.
> Канон данных: `d01_kernel.sql` (Farm domain, 7 сущностей), Dok1 §Farm + §5.1/§5.4. Смежные модули: Feed (`d03`), Vet (`d04`), Ops, TSP (`d02`), Consulting (`d09`).

## Рамка продукта и охват флоу

Базовый модуль «Ферма» = зонтик из трёх узлов: **Профиль хозяйства · Стадо (уровень групп) · План работ (ЦТК)**. Feed/Vet/TSP/Consulting *втыкаются* в него как ценность, но проектируются отдельно.

Ядро идеи — **прогрессивное накопление данных**: система полезна на любом уровне полноты (P11); фермер отдаёт данные в обмен на конкретную ценность (план работ, календарь вакцинаций, план рационов), и с каждым касанием профиль фермы наполняется. Позже поверх — сквозной AI-слой («операционный директор фермы»).

**Только мясное скотоводство** (TURAN = ассоциация мясного КРС). Направление продуктивности — константа, не спрашивается.

**Граница ERP (D20):** AgOS работает на уровне **групп** (`herd_groups`), не отдельных животных. Поголовный учёт (ERP, уровень L4) — конечная точка прогрессии, не старт.

## Архитектура модуля (функциональная)

Эта итерация фиксирует **скелет**, не контент (F-D8). Пять сущностных слоёв:

```
   AI-слой (позже)  ─────▶  «Операционный директор фермы»
                            (читает весь контекст фермы, ведёт проактивно)
                                     ▲
   ────────────────────────────────────────────────────────────────────
   Слой ЦЕННОСТИ        План работ(ЦТК) · Вакцинация(Vet) · Рационы+корма(Feed)
   (крючки, обмен            · [Продажи·TSP] · [Фин-модель·оборот стада·Consulting]
    данные↔ценность)        отдают конкретную пользу → пишут данные обратно в профиль
                                     ▲
   ────────────────────────────────────────────────────────────────────
   Слой ЦТК-ДВИЖОК      Шаблон ЦТК (стандарт, версионируется, per архетип×отёл — P8)
   (Узел 2)                 └─▶ Инстанс ЦТК (ферма×год) = шаблон ∘ профиль фермы
                            3 слоя (F-D6); точность растёт с полнотой профиля
                                     ▲
   ────────────────────────────────────────────────────────────────────
   Слой ЯДРО «Ферма»    Профиль фермы ── Стадо (группы) ── Журнал событий
                            farms          herd_groups        herd_events
                            (архетип,      (по категориям:    (append-only,
                             содержание,    маточное/молодняк/  17 типов)
                             отёл, локация)  бычки/быки…)
                                     ▲
   ────────────────────────────────────────────────────────────────────
   Слой ДАННЫЕ         L1 регистрация · L3 опросник(кабинет) · L2 AI(WhatsApp) · L3 подтверждение · L4 ERP
   (прогрессия)             data_source(+confidence — рамка {стадо, корма}, см. F-Q8); полезно на любом уровне (P11)
```

**А1. Ядро.** Модуль владеет тремя сущностями: `farms` (паспорт), `herd_groups` (стадо на уровне групп, D20), `herd_events` (журнал). Всё остальное — читатели этого ядра.

**А2. Прогрессивная модель данных — несущий принцип.** `data_source`+`confidence` несут **стадо (`herd_groups`) и запас кормов** (рамка канона, F-D10); полнота **профиля фермы** = вычисляемый % заполненных полей (без хранимого `confidence`). Каждое касание платформы поднимает достоверность (data flywheel, Dok1 §5.3/§5.4); higher-confidence перезаписывает lower (D21). Модуль полезен при любой полноте (P11) — это и есть ответ на «фермер не хочет вести учёт».

**А3. ЦТК-движок = шаблон ∘ профиль.** Есть **шаблон** (канон, версионируемый стандарт per архетип×система-отёла — P8) и **инстанс** (наложение шаблона на конкретный профиль → даты/фазы/задачи). Чем полнее профиль — тем точнее инстанс. Форма — 3 слоя (F-D6). **Контент шаблонов — отдельные итерации.**
> ⚠️ **Движок уже построен** (architect G2, F-D9): `d05_ops_edu.sql` — `production_cycle_templates`+`phase/task/kpi_templates`+`sop_documents` (шаблон), `fn_generate_production_plan()` (оператор ∘), `farm_production_plans/farm_phases/farm_tasks/farm_kpis` (инстанс). Модуль **дозаполняет контент + ветвит по архетипу**, а не строит движок. Контент репродукторного шаблона — в scope первой продуктивной итерации (иначе JTBD «план за 3 минуты» пустой, R4).

**А4. Слой ценности = движок вовлечения.** Смежные модули цепляются к ядру как «крючки»: каждый предлагает конкретную пользу за минимум данных и пишет данные обратно в профиль. Порядок: План работ (Ops/ЦТК) → Вакцинация (Vet) → Рационы+корма (Feed) → [позже] Продажи (TSP) → [позже] Фин-модель/оборот стада (Consulting).

**А5. Границы (P4).** Ферма владеет ядром + инстансом ЦТК (`farm_production_plans`/`farm_phases`/`farm_tasks`). Инстанс запускается **self-service** (фермер → `draft`, F-D12); эксперт — опциональная доводка. Feed/Vet/TSP/Consulting **читают** стадо/профиль и возвращают ценность; их данные живут в их доменах. Три параллельных плана (Ops↔Feed↔Vet) координируются через HerdGroup + перекрытие дат, не через FK (Dok1 §5.1).

**А6. Архетип — сквозной параметр.** Репродуктор / Откорм / Полный цикл ветвит: опросник, шаблон ЦТК, категории стада, набор крючков. Канон словаря для ЦТК = `farm_type`; мост `activity_type→farm_type` (`mixed→combined`, F-D11). Приоритет разработки — репродуктор (F-D8).

**А7. Реконсиляция с построенным (⚠️ HS-1/2/5).** В коде уже есть: `FarmProfile`, `herd/{HerdOverview,HerdGroupForm}`, `plan/{ProductionPlan,TaskList,Timeline,CascadePreview,KpiDashboard}`, 9 RPC (`rpc_upsert_farm`, `rpc_upsert_herd_group`, `rpc_log_herd_event`, `rpc_get_farm_summary`, `rpc_get_farm_tasks`, …). Архитектура ложится на это **аддитивно**; отдельный шаг — сверка «что построено vs что нужно» (карта покрытия), чтобы не дублировать и не ломать.

## Глоссарий полевых терминов

| Термин | Значение (со слов CEO, подтверждено) |
|---|---|
| **Репродуктор** | бизнес-модель: маточное поголовье + репродукция; конечный товар — отъёмыш |
| **Откорм** | бизнес-модель: закуп отъёмышей → доращивание → финишный откорм → убой |
| **Полный цикл** | все стадии на одной ферме (редко) |
| **Отъёмыш** | телёнок ~6 мес, отнятый от матери; товар репродуктора / сырьё откормочника |
| **Доращивание** | стадия роста после отъёма (до ~10–12 мес). **Модификатор, не архетип**: может быть хвостом **репродуктора** (продаёт подрощенного, а не отъёмыша) ИЛИ фазой **откорма** |
| **Маточное поголовье** | коровы-матки репродуктора |
| **Система отёла** | сезон отёла: весенний / осенний / круглогодичный / два сезона |
| **ЦТК** | Циклическая Технологическая Карта — годовой план работ фермы (что/когда/как + SOP + задачи); форма зависит от архетипа |

## Лог решений и открытых вопросов

### Решения (подтверждено CEO)
- **F-D1** — Продукт только для **мясного** скотоводства; направление продуктивности из опросника исключено.
- **F-D2** — **Архетип + модификатор.** Базовые архетипы: **Репродуктор / Откорм / Полный цикл**. **Доращивание — модификатор, не архетип**: у репродуктора = «продаёт подрощенного 10–12 мес, а не отъёмыша»; у откорма = внутренняя фаза. Влияет на стадо, длительность цикла, экономику.
- **F-D3** — **ЦТК ветвится по архетипу**: репродуктор = **сезонный годовой календарь** (спина — система отёла: отёл→случка→отъём[→доращивание]); откорм = **непрерывный операционный поток** (перманентный закуп, стадо разновозрастное, сезоны вторичны). `calving_system` релевантен только репродуктору.
- **F-D5** — «Годовой план работ» как первая ценность чисто ложится на **репродуктора**. У **откорма** первая ценность, вероятно, иная: корма + контроль привеса + момент вывода на убой (мостик в Feed/TSP). Крючок вовлечения для откорма — иной (уточняется, F-Q6).
- **F-D6** — **ЦТК = 3 слоя** (подтверждено ресёрчем US/AUS/CAN, F-Q5 MIX): (1) **сквозной годовой вет-календарь** — по датам, для всех групп; (2) **цикл группы/партии** — по весу/дням-на-корме (приёмка→фазы рациона→выход по целевому весу); (3) **ежедневный контроль состояния** — обход/отбраковка. Репродуктор: доминирует сезонный производственный календарь (отёл/случка/отъём) + слой-1. Откорм: доминирует слой-2 (цикл партии) + слой-1. Для малых/средних — **без enterprise-DOF-оптимизации**: типовой шаблон-календарь, кастомизируемый (P8, не менять процесс фермера).
- **F-D7** — Гранулярность стада откорма в v1 = **один пул** (общее поголовье + средний вес). Партии-когорты — прогрессивно позже (лестница L1→L4, P11/P3).
- **F-D8** — **Высота этой итерации = архитектура модуля.** Детальный контент ЦТК (конкретные фазы/задачи/SOP по каждому архетипу) — **отдельные последующие итерации**. Приоритет разработки: **репродуктор/продуктор** вперёд откорма (откорм важен, но позже).
- **F-D9** — **G2 sign-off (architect, 2026-07-08): APPROVE-WITH-CONDITIONS → условия решены CEO (см. F-D10/11/12).** Архитектура аддитивна и опирается на канон. Открытие: движок ЦТК уже построен в `d05` (см. A3). Риски **R1** (откорм-цикл по весу не ложится на date-based `farm_phases` + `idx_farm_plan_one_active` — не закрывать этот путь при проектировании репродуктора), **R2** (`breeding` уже в обоих enum — учесть в F-Q2), **R3** (модуль держится на Event Bus — Dok4 §5.5, опираться, не проектировать заново), **R4** (контент репродукторного шаблона — критический путь ценности).
- **F-D10** (C1, CEO 2026-07-08) — Layered Truth **сужен до канона**: `confidence` — только `herd_groups` + `FarmFeedInventory`. Полнота профиля фермы = **вычисляемый %** заполненных полей, без хранимой колонки на `farms`. Схема не меняется (P4).
- **F-D11** (C2, CEO 2026-07-08) — Канон словаря архетипа для ЦТК = `production_cycle_templates.farm_type`. Мост `activity_type→farm_type`: `cow_calf→cow_calf`, `finishing→finishing`, `mixed→combined` («полный цикл»), `breeding→breeding`; `dairy` не применяется (F-D1). Аддитивно (P6/P8).
- **F-D12** (C3, CEO 2026-07-08) — Инстанс ЦТК запускается **self-service**: фермер → мгновенный `draft`-план из шаблона; эксперт — **опциональная доводка** (`draft→active`). `expert_profile_id` nullable-путь, аддитивно; каноничный expert-in-the-loop сохраняется как upgrade, не как gate.
- **F-D4** — «Минимально достаточный» набор данных опросника **зависит от архетипа**.
- **F-D13** (CEO 2026-07-10) — **Scope ARS-170 = опросник + видимый план.** Job Узла 1 («получи план») не закрыт, пока фермер не видит результат. Поэтому ARS-170 включает: опросник (репродуктор) → генерацию draft-ЦТК (мост F-D11 + `rpc_start_production_plan`) → **фикс FARM-01** (`rpc_get_production_plan` селектит несуществующие колонки — единственный читатель draft-плана) → показ плана. Активация draft→active (FARM-02) остаётся в ARS-172. Обоснование: без payoff опросник ломает ядро механики «данные↔ценность» (P9).

## Узел 1. Первичный профиль фермы (ненавязчивый опросник)

**Статус: спроектирован (репродуктор-ветка, 2026-07-10).** Приоритетный путь (репродуктор) готов к сборке — ARS-170. Откорм-ветка ждёт F-Q6 (крючок вовлечения), детализируется отдельной итерацией (F-D8).

### 1. Контекст в реальности
- Сегодня есть только web+mobile фермера. При регистрации создаётся организация типа «ферма»; достоверно известно только: название фермы, регион, локация. Онбординг трогает основную породу. Скот частично проясняется при публикации партии в TSP.
- Всё остальное о ферме — пусто. Фермер не мотивирован «вести учёт»: ценность отдалена.

### 2. Job (JTBD)
Фермер тапает вкладку «Ферма» — он хочет **получить конкретную пользу** (план на год), а не «заполнять анкету». Опросник = обмен «6 базовых фактов → готовый годовой план». Успех: за ~3 минут без усилий получил ценность, система записала минимально достаточный профиль.

### 3. Функциональные требования
- При входе во вкладку «Ферма» с незаполненным профилем — ненавязчивое предложение заполнить базу («сформируем план работ на год»).
- Один **разветвляющий вопрос — архетип** (репродуктор / откорм / полный цикл), далее ветка полей. «Племенное» — **не** отдельный архетип, а способ продажи приплода внутри репродуктора (F-Q2 закрыт каноном).
- Известное из регистрации/онбординга **не переспрашивать** (F-Q3 закрыт): регистрация уже даёт **название хозяйства · область · район · основную породу** (`FarmerDetails.tsx`) → опросник открывается сразу на архетипе, эти поля не спрашивает (предзаполняет из профиля организации).
- Заполнение — прогрессивное: можно пропустить/отложить, профиль полезен частично (P11).
- **Payoff-петля (F-D13):** завершение минимума ветки → мост `activity_type→farm_type` (F-D11) преселектит шаблон ЦТК → генерация draft-инстанса (`rpc_start_production_plan`) → **фермер сразу видит готовый годовой план** (Job закрыт). Показ плана требует рабочего читателя — фикс **FARM-01** входит в scope ARS-170 (см. F-D13).

### 4. Данные

Общие поля (все архетипы):
| Поле фермера | Куда пишется |
|---|---|
| Архетип (репродуктор/откорм/полный цикл) | `farm_activity_types.activity_type` (cow_calf/finishing/mixed) |
| Формат содержания | `farms.shelter_type` (stall/pasture/mixed/feedlot) |
| Общее поголовье | Σ `herd_groups.head_count` |

Ветка **Репродуктор** (подтверждено):
| Поле | Куда пишется |
|---|---|
| Система отёла (весна/осень/…) | `farms.calving_system` |
| Маточное поголовье | `herd_groups` (категория = маточное), `head_count` |
| Доращиваешь молодняк перед продажей? (отъёмыш ~6 мес vs подрощенный 10–12 мес) | модификатор → доп. `herd_group` молодняка + длиннее цикл (F-D2) |

Ветка **Откорм** (F-Q1 закрыт → поток непрерывный, тайминг не спрашиваем): поголовье на откорме · целевой вес убоя · содержание (обычно feedlot). Точный обязательный минимум зависит от F-Q5.

Запись достоверности: `data_source` = `platform` (L3, confidence 75) при ручном подтверждении фермером; `registration` (L1, 25) для того, что уже пришло из регистрации.

### 5. Логика и бизнес-правила
- Направление = мясное (константа, F-D1) — не поле.
- Обязательность полей **зависит от архетипа** (F-D4): репродуктор ⇒ система отёла + маточное (+ модификатор доращивания); откорм ⇒ целевой вес + поголовье (детализация по F-Q5).
- «Минимально достаточно» = набор, которого хватает, чтобы сгенерировать ЦТК (Узел 2). Ниже порога — ЦТК не строится, но профиль сохраняется. **Порог репродуктора = система отёла + маточное поголовье (>0)**; при нём генерируется draft-ЦТК.
- Higher-confidence перезаписывает lower (D21).
- **Генерация ЦТК (F-D13):** при достижении порога опросник вызывает мост `activity_type→farm_type` → преселект шаблона → `rpc_start_production_plan` (draft, self-service, F-D12). Активация draft→active (FARM-02) — не в scope 170, это ARS-172.

### 6. Состояния и краевые случаи
- Пусто (новый фермер) · частично заполнено (пропустил ветку) · офлайн (полевой ввод) · данные из TSP/онбординга уже есть (предзаполнение) · фермер не знает точное поголовье (грубая оценка допустима, L1).

### 7. Критерии приёмки (репродуктор, ARS-170)
- [ ] Опросник открывается на выборе архетипа; поля регистрации (название/область/район/порода) не переспрашиваются, предзаполнены.
- [ ] Ветка репродуктора собирает минимум: система отёла + маточное поголовье (+ вопрос о доращивании как модификатор).
- [ ] Частичное заполнение сохраняется и не блокирует профиль (P11); можно выйти и вернуться.
- [ ] Данные ложатся в `farms` (`shelter_type`/`calving_system`) / `farm_activity_types` / `herd_groups` без потерь, с корректным `data_source`/`confidence` (`platform`/L3 при ручном вводе).
- [ ] При достижении порога (отёл + маточное) — генерируется draft-ЦТК через мост F-D11 + `rpc_start_production_plan`.
- [ ] **FARM-01 починен** → сгенерированный план **реально отображается** фермеру (payoff, Job закрыт), без runtime-ошибки.
- [ ] Опросник живёт в primary `/cabinet` shell (не legacy), переиспользует существующие RPC (аддитивно, HS-1/2/5).

### 8. Открытые вопросы
- *(F-Q1, F-Q2, F-Q3 закрыты — см. лог решений.)* Для откорм-ветки остаётся F-Q6 (крючок вовлечения) — вне scope ARS-170.

## Референс-данные для шаблонов ЦТК (P8 — стандарты как данные, версионируются)

> Seed-значения из практики US/AUS/CAN. **Сверить с KZ-породами** (казахская белоголовая, ангус, герефорд, аулиеколь) и с внутренней моделью `Docs/Zengi.Farm_Model farm_020426_v10_WintSumm.xlsx` при проектировании Узла 2.

**Откорм — цикл партии (слой 2):**
- Приёмка (день 0–7 от постановки, единая обработка): вакцинация (респ. комплекс IBR/BVD/PI3/BRSV + клостридиоз 7-way + пастереллёз), дегельминтизация, имплант (где применим), бирка/ID, взвешивание. Ревакцинация через 10–14 дн обычно не нужна.
- Адаптация/стартовый рацион ~14 дн → доращивание (grower) ~60–100 дн (ADG ~0.7–1.1 кг/дн) → финиш (finisher) ~30–100 дн (ADG ~1.1–1.8 кг/дн).
- Готовность к финишу ~385–450 кг; убойный финиш ~570–635 кг.
- Слой 3: ежедневный обход, отбраковка/лечение (BRD = 50–90% болезней/падежа фидлота).

**Репродуктор — сезонный производственный календарь:**
- случка → отёл → вакцинация (пред-случная / пред-отёльная) → отъём (~6 мес) [→ доращивание 10–12 мес, если модификатор] → прег-чек / выбраковка; дегельминтизация; всё привязано к сезону отёла (`farms.calving_system`).
