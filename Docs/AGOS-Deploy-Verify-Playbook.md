# AGOS Deploy & Verify Playbook

> Единственный прод-Supabase (`mwtbozflyldcadypherr`), staging нет. SQL деплоится вручную
> (не через `supabase_migrations.schema_migrations` — этот реестр для прод-изменений пуст).
> До 2026-07-25 деплой шёл 4 разными каналами (`deploy_sql.py`, `deploy_d07.py`,
> `deploy_tsp_matchfix.py`, `deploy_vet_isolation_fix.py`, плюс ad-hoc psycopg2 и ручной
> SQL Editor) — ни один не оставлял следа, поэтому «что реально на проде» восстанавливалось
> археологией по DECISIONS_LOG и памяти агентов. Этот плейбук фиксирует единый канал
> (`scripts/deploy.py`) + дисциплину верификации вокруг него. Читать перед любым деплоем на
> прод и при ревью PR, который его касается.

---

## 1. Канал деплоя — `scripts/deploy.py`

Единственный способ применить SQL на прод. Общий слой (пароль, коннект, канонический
список файлов, парсинг тел функций) вынесен в `scripts/agos_db.py` — им же пользуется
`scripts/prod_diff.py` (§3), чтобы деплоер и дрейф-детектор не расходились в том, что
считать «каноном» (P4).

```bash
python3 scripts/deploy.py --list                   # что применено / что pending
python3 scripts/deploy.py --files d05_ops_edu.sql  # точечно — обычный случай
python3 scripts/deploy.py --migrations             # только новые supabase/migrations/*.sql
python3 scripts/deploy.py --all                    # d-файлы + миграции — полный реплей
python3 scripts/deploy.py --files d07 --dry-run    # план без применения
```

| Флаг | Что делает |
|---|---|
| `--files a,b` | Через запятую, с `.sql` или без; матчит канонические источники (`by_name`/префикс) |
| `--migrations` | Только ещё не применённые (по sha) `supabase/migrations/*.sql` |
| `--all` | `DOMAIN_FILES` (d01→d14, см. CLAUDE.md) + миграции по времени |
| `--dry-run` | Печатает план (файл, размер, sha), ничего не применяет |
| `--note "ARS-NNN"` | Комментарий в журнал |
| `--force` | Применить даже если sha уже залогирован (обычно не нужно) |

**Пароль:** только `.db_password` (repo-root, gitignored) или `AGOS_DB_PASSWORD`. Никогда
не передавать паролем через argv — виден в `ps` и остаётся в истории шелла
(`scripts/agos_db.py:read_password`).

**Денилист арм-DDL:** `MIGRATION_DENYLIST` в `agos_db.py` — миграции, которые `--all`/
`--migrations` пропускают молча (пример: `20260717120000_membership_renewals_pg_cron.sql` —
армирование движка продлений членства раздало бы бесплатные продления живым организациям
при ещё-stub платёжном провайдере, D-BILL-CRON-STAGING-01). Такие миграции — только явным
`--files`, после отдельного решения CEO/G3.

### `ops_deploy_log` — учётная книга

Таблица в `d01_kernel.sql` (секция «ops_deploy_log»). Пишется `deploy.py` **в той же
транзакции**, что и сам применяемый файл — строка появляется ТОЛЬКО если применение
закоммичено; откат/ошибка не оставляет ложной записи. Колонки: `file_name`, `kind`
(`domain`/`migration`/`adhoc`), `sha256` применённого текста, `git_sha`+`git_dirty` (грязное
дерево ⇒ sha в журнале не описывает применённый текст точно), `applied_at`/`applied_by`
(роль БД)/`host_user` (OS-пользователь), `note`. Служебная: RLS включена без политик,
`revoke all from public, anon, authenticated`, `grant all to service_role` — приложение к
ней не ходит.

**После коммита файла `deploy.py` сам сверяет тела функций с `pg_proc`** (`verify_bodies`)
и печатает `⚠ VERIFY`, если каноническое (последнее в файле) тело не найдено на проде —
это ровно сигнатура L-1 («более позднее определение того же имени в файле молча перетирает
фикс»).

## 2. Порядок: SQL ↔ фронт

SQL-деплой (через `deploy.py` или MCP `apply_migration`) уходит на прод **мгновенно**.
Фронт деплоится **отдельно** — Vercel собирает из смёрженного `main`, и это может отставать
от момента, когда PR технически «замержен», на минуты-часы. Отсюда системный риск: если
SQL-деплой отзывает/переименовывает контракт, который живой (уже задеплоенный) фронт всё
ещё зовёт напрямую — прод ломается ДО того, как новый фронт встанет.

**Реальный инцидент (ARS-311/312, 2026-07-23/24):** ревок прямого EXECUTE у
`fn_shift_phase_cascade`/`fn_preview_cascade` (D104-каскад) ушёл на прод раньше, чем
Vercel-билд с переводом F8-превью на новую guarded-обёртку `rpc_preview_breeding_shift`
(PR #142) стал реально live — экран превью каскада сломался. Мост: временный re-grant
`authenticated` на `fn_preview_cascade` (безопасно, т.к. функция **самогардирована**, L-7 —
своя guard-CTE) через миграцию `ars311_temp_regrant_fn_preview_cascade_pending_frontend`,
с отдельной задачей **ARS-312** на ре-ревок. ARS-312 закрыт только после того, как «фронт
реально live» было доказано эмпирически — выкачаны и прогреплены все 225 JS-чанков,
отданных `turanstandard.kz`: `rpc_preview_breeding_shift` присутствует, `fn_preview_cascade`/
`CascadePreview` отсутствуют во всех чанках — только тогда применён финальный ревок
(`ars312_re_revoke_fn_preview_cascade_authenticated`).

**Правило:**
1. Деплой **аддитивной** обёртки/нового контракта — ничего не ломает (старое ещё живо).
2. Дождаться, что фронт на новом контракте **реально live** (не «PR смёржен» — смёржен ≠
   задеплоен; проверить фактические JS-чанки на проде, как в ARS-312, либо дождаться
   подтверждённого Vercel-деплоя).
3. Только ПОТОМ — `revoke`/удаление старого контракта.

**Если ревок уже уехал и фронт ломается:** временный re-grant допустим ТОЛЬКО если функция
самогардирована (не течёт при прямом вызове чужим тенантом) — и сразу завести отдельную
задачу на повторный ревок (не оставлять «временное» неотслеженным).

**Профилактика (до деплоя ревока/переименования):** `grep "supabase.rpc('<fn>'" src/` —
раскопать frontend-coupling ДО деплоя, не после.

## 3. Верификация после деплоя

### 3.1 `scripts/prod_diff.py` — дрейф прод↔git

```bash
python3 scripts/prod_diff.py            # отчёт в консоль
python3 scripts/prod_diff.py --json     # машинный вывод (дозор/CI)
python3 scripts/prod_diff.py --strict   # exit 1 при любом дрейфе
```

Читает прод read-only (`default_transaction_read_only`), сравнивает нормализованные тела
функций `public` с каноном (d-файлы → миграции, позднее определение выигрывает — семантика
применения PostgreSQL). Пять классов:

| Класс | Значит |
|---|---|
| `merged-not-deployed` | Есть в git, отсутствует на проде (ARS-266-класс: «done» = только мерж) |
| `body-divergent` | Имя есть у обоих, каноническое тело не найдено на проде (L-1: перетёрто более поздним def) |
| `prod-only` | Функция на проде, в git нет (hotfix мимо канона) |
| `extra-overloads` | На проде сигнатур больше, чем определяет git (риск `PGRST203`) |
| `acl-divergent` | Грант на проде ≠ канону: `revoke ... from anon` лежит в git, но на БД не применён — тела совпадают, дыра открыта (`NOTE-ANON-EXEC-01`, класс ARS-311) |

Плюс инфра-срез: `pg_cron`/расширения, таблицы в публикации `supabase_realtime`, число
строк в `ops_deploy_log`.

**Как считается `acl-divergent`:** из канона парсятся все `grant/revoke execute on
function ... to|from <роль>` (на 2026-07-25 — 139 функций, 341 правило), позднее указание
выигрывает; факт снимается с прода через `has_function_privilege(role, oid, 'execute')`.
Это единственная проверка, ловящая расхождение, при котором и код, и тела совпадают, а
права — нет; ровно на нём строились инциденты ARS-311/312 и SEC-NORMS-UPSERT-01.

### 3.2 Probe + rollback — верификация нового/изменённого RPC без прод-побочек

Один Supabase-проект, staging нет — безопасная проверка тела функции против живой схемы:

```sql
begin;
create or replace function public._probe_<name>(...) as $f$ ... $f$ language plpgsql;
-- прогон сценария, результат в temp-таблицу
select ...;  -- ассерты
rollback;
```

- Имя **всегда throwaway** (`_probe_...`) — НИКОГДА не `create or replace` реальный RPC для
  проверки: даже худший случай (частичный коммит) не может испортить задеплоенную функцию.
- `now()` константна внутри транзакции — сравнения вида `next_billing_at = now()` точны.
- Чтобы проверить РЕАЛЬНУЮ задеплоенную функцию (её authz guard + эмиссию событий), а не
  probe-копию: в той же `begin…rollback` `set local request.jwt.claims =
  '{"app_metadata":{"is_admin":true}}'` — `fn_is_admin()`/`fn_my_org_ids()` читают
  `app_metadata` из JWT-claim, guard проходит без реального токена. Переключение claims на
  чужую org доказывает именно **guard самой функции** (не RLS-политику — SECURITY DEFINER
  обходит RLS изнутри, а MCP-соединение привилегированное).
- Net-new слайс (новые таблицы + совершенно новые RPC, нечего перетирать) — можно применить
  весь DDL-блок под РЕАЛЬНЫМИ именами внутри `begin…rollback`: объектов ещё не существует,
  `rollback` дропнет всё целиком.
- `execute_sql` (Supabase MCP) возвращает только результат ПОСЛЕДНЕГО SELECT — разносить
  многошаговую интроспекцию на отдельные вызовы.

**Важная граница метода:** rollback-tx через привилегированное соединение **не ловит**
Supabase-guard `safeupdate` (блокирует `DELETE`/`UPDATE` без `WHERE` для `authenticated`/
`service_role` через API, но НЕ для psql/MCP). Реальный кейс: `rpc_start_production_plan`
делал `DELETE` без `WHERE` на temp-таблице — rollback-tx через MCP дал ложный зелёный,
баг проявился только через реальный браузерный логин. **Правило:** для любого RPC с
`DELETE`/`UPDATE` (даже на temp-таблице) probe+rollback ДОПОЛНЯЕТСЯ проверкой через
реальную аутентифицированную сессию — `scripts/seed_farmer.mjs` (фермер, телефон
`+77010000001` / PIN `123456`) или `scripts/seed_admin.mjs` (admin, email+пароль) — прежде
чем помечать фикс готовым.

### 3.3 plpgsql резолвит имена только в рантайме

`language plpgsql` парсит вложенный SQL **лениво** (при первом вызове, не при
`CREATE`) — битая ссылка на колонку/таблицу спокойно проходит `CREATE OR REPLACE`,
`cross_check.sh` (статический grep) и `tsc`, а падает `column ... does not exist` только
на первом реальном вызове.

**Реальный инцидент (ARS-229):** `rpc_get_demand_board` ссылался на `tsp_skus.name_ru` —
такой колонки нет. Все статические проверки были зелёными, ветка ушла в ревью как
«проверено» — падал бы на каждом вызове. Пойман только сверкой имён колонок с живой схемой
при ревью.

**Правило:** для любого нового/изменённого plpgsql RPC — (1) сверить каждую
колонку/таблицу в теле с живой схемой (`information_schema.columns`), не доверять
статическим проверкам; (2) реально выполнить его (или его внутренний запрос за guard'ом,
через probe+rollback §3.2) до того, как считать готовым.

### 3.4 ACL-ловушки SECURITY DEFINER

Проверка `has_function_privilege('anon'|'authenticated', 'public.fn(sig)', 'execute')`
(или сырой `pg_proc.proacl`) — обязательный шаг ревью для каждого нового/изменённого
SECURITY DEFINER RPC, отдельно от §3.1 (prod_diff тела не проверяет гранты):

- **Ownership guard.** SECURITY DEFINER обходит RLS — если функция берёт клиентский
  `p_organization_id`/`p_user_id` и использует без проверки против
  `fn_my_org_ids()`/`fn_current_user_id()` (с bypass для `service_role`/`fn_is_admin()`) —
  межтенантная утечка/запись.
- **Trap: `revoke ... from anon` не убирает `PUBLIC`.** Postgres вешает
  `EXECUTE TO PUBLIC` на каждую новую функцию по умолчанию — `revoke from anon` его не
  трогает. Нужен явный `revoke execute ... from public`, не только `anon`.
- **Trap 2b: `revoke from public, anon` всё ещё оставляет `authenticated`.** Supabase
  прогоняет `ALTER DEFAULT PRIVILEGES ... GRANT EXECUTE ON FUNCTIONS TO anon, authenticated`
  для каждой НОВОЙ функции — это отдельный ролевой грант, которого `revoke from public,anon`
  не касается. Для внутреннего helper'а (вызывается только definer-RPC как owner, без
  своего guard) это реальная межорг-утечка при прямом вызове от `authenticated`. Нужен
  явный `revoke execute ... from authenticated` тоже — owner всё ещё выполнит её изнутри
  definer-RPC, внутренние вызовы не ломаются.

Самогардированная функция (есть собственная org-guard) — утечки нет даже с «лишним»
грантом, но гигиенически ревок всё равно нужен (defense-in-depth); НЕгардированная —
реальная дыра. Не путать серьёзность одного с другим при разборе инцидента.

## 4. Инфра, которую надо армировать явно

Часть инфраструктуры не включается вместе с DDL — надо проверять/включать отдельно
на каждом слайсе, который на неё рассчитывает.

**Publication `supabase_realtime`.** Была пустой (`puballtables=false`, 0 таблиц) →
`postgres_changes` инертен для ВСЕХ таблиц, пока таблица явно не добавлена:
`alter publication supabase_realtime add table public.<t>` (идемпотентно через
do-block-guard). Найдено при верификации ARS-269: слушатель таксономии
(`useTaxonomyRealtimeSync`) был задеплоен, но молча мёртв на проде, замаскирован
`staleTime=60s` react-query + редкостью правок стандартов. ARS-269 армировал только
`platform_events`. **Правило:** перед постройкой нового `postgres_changes`-слушателя —
проверить, что целевая таблица в публикации, и включить это в тот же слайс. Realtime
уважает RLS, так что публикация RLS-таблицы с org-скоупом безопасна.

**`pg_cron`.** Не установлен на проде. Движок продлений членства/биллинга собран, но
армирующий DDL (`cron.schedule(...)`) сознательно вынесен в отдельную STAGING-ONLY
миграцию (денилист §1) — включение движка = отдельное решение CEO/G3 после замены
stub-платёжного провайдера, не побочный эффект обычного деплоя. `prod_diff.py` печатает
факт наличия `pg_cron` в срезе инфры на каждом прогоне — не полагаться на память,
проверять перед тем, как что-либо завязывать на cron-расписание.

## 5. Чеклист перед деплоем

1. `git status`/`git diff --stat` — понять реальный периметр правки (HS-3).
2. Новый/изменённый plpgsql RPC → сверить каждую колонку/таблицу с живой схемой (§3.3),
   прогнать probe+rollback (§3.2); если RPC делает `DELETE`/`UPDATE` — доп. проверка через
   `seed_farmer.mjs`/`seed_admin.mjs`, rollback-tx одной привилегированной сессии
   недостаточен.
3. Новый/изменённый SECURITY DEFINER → ownership-guard на месте? `revoke` покрывает
   `public` + `anon` + `authenticated` (§3.4), не только `anon`?
4. Ревокаешь/переименовываешь контракт, который уже зовёт живой фронт? →
   `grep "supabase.rpc('<fn>'" src/`; если да — сначала аддитивная обёртка + подтверждённый
   live-деплой фронта, потом ревок (§2). Не наоборот.
5. Новый `postgres_changes`-слушатель → таблица в публикации `supabase_realtime` (§4)?
6. `python3 scripts/deploy.py --files <файл> --dry-run`, затем без `--dry-run`.
   Денилист арм-DDL применять только явным `--files` после отдельного решения (§1).
7. После деплоя: `python3 scripts/prod_diff.py` — 0 дрейфа (или объяснимый), включая
   секцию `acl-divergent` (гранты сверяются автоматически, §3.1).
8. Запись в `DECISIONS_LOG.md` (L-5); при обнаруженном код↔канон разрыве — строка в
   `IMPL_DEBT.md`.
